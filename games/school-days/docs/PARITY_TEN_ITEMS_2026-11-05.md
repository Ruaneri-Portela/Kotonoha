## Additional user feedback before the full rehearsal: ORS fades and Replay Data indicator

### Authored BlackFade/WhiteFade flashes during gameplay

- **Retail source, distinct from menu/transport fades:** `D:\Dev\Preserved\SchoolDaysHQ\ResearchText\FidelityBuild-docs\FADE_RE.md` reconstructs original EXE handler `0x0043AA8C..0x0043AD84`. ORS authored fades run at **24 fps**, with linear integer alpha `floor(elapsedTicks*255/durationTicks)`; `IN` is color→transparent and `OUT` is transparent→color. An event is active on **`[startTick, endTick)`**, never held past its terminal tick. There is **no evidence for forcing a minimum one-second fade**. The user's final, explicit composition requirement is **fade behind subtitles**; do not infer subtitle occlusion merely from the EXE's `Z` event name or scene-item order.
- **Retail corpus:** read-only scan of `Backup Packs Original/Script.GPK` (`audit_fade_near_next.py`, QA-only script under ignored `build/`) examined 1,859 pack index entries and found **1,119 fade events**; **550 `OUT` fades end at the exact `Next` tick**. Example: real `ENGLISH/01/01-00-C03.ENG.ORS` has `BlackFade OUT` tick **72→96**, and `Next` at **96**. Another example `00/00-00-A00` has a **12-tick `BlackFade IN`** at 101→113; short fades can be intentional.
- **Kotonoha divergences and fix:**
  1. The runtime sets `pendingSceneAdvance` on `Next` but actually swaps Script/Gameplay in the *following* `Runtime::update()`. The original OUT fade expires as scripted at `Next`; previously v3 could expose the old background in that extra old-owner render, causing a single-frame flash. `SchoolDaysOrsFadeBoundary::CoversDeferredNext` now identifies **only** the synthetic deferred boundary frame when the `OUT` endpoint equals `Next` and covers it with the fade's original black/white terminal color. It does not extend any ordinary fade or bridge authored gaps.
  2. Original EXE alpha is **integer per tick**; the generic `FadeScene` sampled *fractional* `elapsed` and rounded alpha with `lround`, so brightness could change *inside the same source tick* and produce the wrong final color at end. `FadeScene::current` also admitted the mathematically exclusive end tick (`<=end`), causing one fully opaque frame at the end of some `OUT` fades even when the ORS already expired. `SchoolDaysOrsFadeFrame::AtTick` is now the single game-specific renderer, projecting `floor((tick-start)*255/duration)` (OUT), or `255-q` (IN), only on `[start,end)`. It respects `eventTouched`, the specific Next cover rule, and black/white colors. **Final user correction:** `Runtime::renderGameplay` draws the ORS color veil **after media/background but before the subtitle layer** (currently `SchoolDaysRuntime.cpp:3365-3395`), so subtitle glyphs remain legible at full fade alpha; physical frontend/transport fades are distinct. Generic `FadeScene` is unchanged and no ORS durations or script events were rewritten. `framePrimaryReady` excludes only the frames with original or synthetic full-coverage alpha 255.
- **Additional corpus audit:** of 899 OUT events, 550 end exactly at `Next` and **348 end before `Next`**. An original 1-tick gap appears in `01/01-00-E06` (`BlackFade OUT` 981→1005, `Next`1006); it must become transparent on tick1005. There were no overlaps between fade events in this original script corpus, and no multiple competing OUTs ending at a shared Next. `01/01-00-C05` has adjacent 12-tick WhiteFade OUT 44→56 / IN 56→68 — they must remain distinct and not be merged or stretched.
- **Tests and visual evidence:** `SchoolDaysSceneTimelineTest::TestRetailOrsFadePresentationBoundary` verifies exact black/white endpoints and prohibits extending a real authored gap or `IN`. `TestRetailOrsFadeIntegerAlpha` asserts **all 12 native A00 IN alphas** (255,234,213,192,170,149,128,107,85,64,43,22), C03-style OUT floor alpha at tick94=233, original exclusive endpoint, deferred terminal-frame color, and E06's authored gap. Targeted DEV script `qa_ors_fade_boundary.py --node 01/01-00-C03` (local ignored QA script) recorded progressive darkening at ticks **66/78/88/94** and a dark outgoing/incoming handoff at `01/01-00-D00`, captures `v3-ors-boundary-C03-*`. `qa_ors_fade_C05.py` also captured the real 12-tick WhiteFade OUT/IN reveal without stretching (`v3-ors-boundary-C05-*`). These directly support the two identified flashing/early-expiry causes; **not all 1,119 authored fade paths have been compared frame-by-frame**.

## Final additional pass: General Options, physical Display, and choice-result musical cue

### Native General Options and remaster Display: retail facts vs later user-requested coupling

- **Original retail evidence:** General `Wide/Standard` and `Full/Window` select an authored interface/layout projection (including `Config.DAT` field `WindowMode`/`W`). That original state machine does not, by itself, establish the current Windows/SDL desktop-mode contract. A native writer for `W` was not authenticated.
- **Final revised player requirement (replacing an intermediate remaster implementation):** General `WIDE/STANDARD` selects the respective authored layout and persists its preference; in physical FULL, STANDARD vertically compresses the full Novel content to 75% of the canvas height, Wide restores 100%. General `FULL` selects native-desktop **borderless** (never Exclusive); `WINDOW` selects the Windows-native **maximized decorated window** so its title bar Min/Max/Close remain visible. The GENERAL aspect/window semantics remain; **later user feedback superseded the third-tab requirement**: on Windows it now opens a School Days-only `Option_Display` page driven by external user artwork, while the generic Kotonoha `SettingsMenu` still exists for other games. See `DISPLAY_OPTIONS_USER_ART_2026-11-05.md`. The generic `DisplayModeCatalog` enumerates all monitor-supported native Windows resolutions and refresh rates with a scrollable selector; the game does not need to know those hardware details. Native B/D/W family semantics remain separate from the physical remaster adaptation and are not claimed as Windows-contract facts of v1.02. Final evidence: `GENERAL_DISPLAY_REVISED_USER_CONTRACT_2026-11-05.md`; the earlier `GENERAL_SOUND_DISPLAY_SYNC_2026-11-05.md` is intermediate/historical.
- **Other audited controls:** subtitles (`TextView`), skip-unread, skip-until-next-decision, Auto and MenVoice, BGM/SE/Voice levels 0..10, mute and relevant defaults/persistence were compared with the native configuration and existing model. `Runtime::applyConfig` applies gains to the BGM/SE/Voice channels. The Sound page previously attempted `SDL_RenderTexture` with a zero-width source when a level was zero; `SchoolDaysSystemUi.cpp` now skips empty-source sprites while preserving native layout. `SchoolDaysDisplayPolicyTest` and `SchoolDaysRuntimeConfigStorageTest` cover these distinctions. - The final engine-wide `SettingsMenu` uses `Kotonoha::DisplayModeCatalog`: on Windows the 32-bpp native `EnumDisplaySettingsExW` mode table for SDL-selected `HMONITOR` is authoritative; SDL fullscreen enumeration is a platform/failure fallback, avoiding 8 observed SDL/DXGI duplicate variants. ### Stability: initial exception and secondary FreeType crash both addressed

- Historical baseline: Release `control2` built and three earlier *sequential* CTest runs passed **57/57**, but `--parallel 4` passed only **53/57**. Four minidumps for `SchoolDaysHandoffRuntimeTest`, child `SchoolDays.exe` of LauncherTest, `SchoolDaysMediaTest`, and `SchoolDays.ExitRuntime` had `0xc0000005` in **freetype.dll 2.14.3 `FT_Done_Face+0x27`**, with `FT_Face.internal==nullptr` (RAX=0) while SDL_ttf closed `GameScene.choiceFont`. Older dumps outside the same parallel test had the same signature, so parallelism was **not** intrinsically required to trigger the secondary crash.
- Deeper forensic examination of two fresh minidumps recovered MSVC C++ exception metadata (`0xE06D7363`) with original `std::runtime_error`, alongside C++ unwind frames during partially constructed `Application/Engine`. `Engine::Engine` constructs two UI/TTF sessions before calling `Runtime::init`, which constructs the game-specific `GameScene.choiceFont`; if an exception occurs afterward, `Engine`'s partially constructed members destroy both TTF sessions **before** the separately owned `Runtime::~Runtime` closes the choice font. The last `TTF_Quit` deinitializes FreeType with that face still open, and subsequent `TTF_CloseFont` can fault. Ordinary shutdown destroys `GameScene` before `Engine` and is not the demonstrated case. This explains the secondary crash without alleging an unidentified data race or corrupting ORS assets.
- **Reproducer:** `SchoolDaysExitRuntimeTest::checkFontLifetimeAcrossEngineConstructorException` forces a controlled exception *after* Runtime init using a translation-dump destination under an isolated test directory. In serial before the fix, the test crashed with `SEGFAULT`; after the fix it passed (1/1, 5.17 s), then continued the original EXIT-flow assertions. **Fix:** `SchoolDaysScenes.hpp::GameScene` now owns `Kotonoha::TTFSession choiceFontTtfSession`, declared **before** `choiceFont`, so the font closes before its own final `TTF_Quit` even if UI construction unwinds. No generic engine semantics changed.
- **Primary error exposed:** repeating the full suite with `--parallel 4` after that lifetime repair produced **51/57**, this time failing with explicit `DEV bridge could not bind 127.0.0.1` in multiple game Runtime tests. `DevBridge` was binding the hard-coded **127.0.0.1:47321** by default in each test process. Distinct CTest processes were contending for this single port; the prior FreeType bug could mask that initial exception. The separate `SchoolDaysRuntimeConfigStorageTest` run also showed `0xc0000409` during this collision window; do not automatically label that code FreeType.
- **Isolated CTest fix:** `games/school-days/tests/CMakeLists.txt` assigns a separate, deterministic `KOTONOHA_DEV_PORT` starting at 47520 for each runtime-bearing test and launcher child on DEV_CONTROL Windows builds. Existing SDL dummy driver and PATH environment settings remain; normal interactive/default DEV port 47321 and retail behavior are unchanged. With this configuration, full rebuild `control2` succeeded and full **`ctest --parallel 4` passed 57/57 in 15.42 seconds**. This establishes successful parallel execution for the exercised suite, not general immunity to every future error path.

## Important constraints

- School Days-specific policies stay under `games/school-days`, not in the generic
  Kotonoha Engine. No old retail executable or archives are copied into source.
- Sound at 16x/32x is silent because the original's internal >4 threshold is
  based on rates **12x/24x**, not the literal button artwork. Whether UI click
  effects remain audible was not isolated from all retail PCM channels.
- The outgoing 500 ms and incoming 1000 ms transport fades are from static
  retail instructions, rather than estimates based on frame-sampling lag.
- Never replace an uncertain observation with a fabricated constant. The
  complete clean-profile-first-ending trial requires explicit user approval.
